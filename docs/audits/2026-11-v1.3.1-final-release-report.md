## B. What is in it

### B1. The three fixes (from `b55a941`, now shipped)

1. **DSH `session.v*.jsonl.zstd` discovery.** The adapter globbed only
   `session.jsonl.zstd`, so every session written after DSH 0.2.1-rc.3 renamed
   its transcript was invisible — `scan` printed a clean total with no warning.
   Discovery now takes the union, and `scan` warns when it finds
   session-shaped files no known pattern claims. That warning is the part that
   matters: the next rename will be loud instead of silent.
2. **UTF-8 stdout on Windows.** `voyager` and `voyager-mcp` force UTF-8 at the
   entry point (`util.force_utf8_stdio`), so the DSH bridge's UTF-8 decode is
   correct without an environment variable. Verified at byte level with
   `PYTHONIOENCODING=gbk`.
3. **Short CJK queries.** FTS5 trigram cannot see fewer than three characters,
   so `voyager search 补丁` returned 0 rows and looked like "not in the index".
   Queries under three characters now take a literal `instr()` scan over the
   same `event_fts.body` the index stores, ordered by `ts` (never `rowid`), with
   `idx_events_ts` added. Measured on 469k events: **2.2 ms** when the phrase
   occurs, **~0.44 s** when it does not (proving absence requires the scan).

### B2. Release-engineering change in this round

`scripts/check_consistency.py` gained a strict mode, and **strict is the default
when `CI` / `GITHUB_ACTIONS` is set**. A `NEEDS_ONLINE` result used to print and
exit 0, which meant "we could not verify the metadata" read as success. The
default lives in the script rather than in the workflow's command line, so the
gate cannot be removed by editing one YAML line; `--no-strict` is the explicit
escape hatch. `--online` now really runs `git ls-remote` for the exact tag
(`v1.3.10` and `v1.3.1-rc1` are tested not to match `v1.3.1`), and
`--require-plugin` refuses to skip the cross-repo bridge check at a release
gate.

Tests: 25 in `tests/test_consistency.py` (was 9).

## E. Rollback

Nothing is migrated. A v1.3.0 install reads a 1.3.1-written index and ignores
the extra index; a 1.3.1 install reads a v1.3.0 index and adds one index. There
is no downgrade script because there is nothing to undo.

The one irreversible action in a release is the tag itself: **do not move it**.
v1.3.0 already has a README pin that landed one commit after the tag; the same
mistake here would make `@v1.3.1` install a tree whose README names `@v1.3.0`.

## F. Publish steps (for the maintainer, not executed)

1. Confirm `git rev-parse HEAD` is the intended commit and the tree is clean.
2. `python scripts/check_consistency.py --strict --online --require-plugin --plugin-root ../dsh-sessionflow`
3. Build again from that commit; compare SHA-256 with the table above.
4. `git tag -a v1.3.1 -m "v1.3.1"` and push the tag.
5. Create the GitHub Release from `docs/releases/v1.3.1.md`, attach both files.
6. PyPI is still manual and `voyager` is still taken upstream; install remains
   `pipx install "voyager @ git+...@v1.3.1"`.
7. After the release exists, update the README pin to `@v1.3.1` in a separate
   commit (this is what v1.3.0 got wrong).

## G. Known gaps, unchanged by this release

- **macOS is not in CI.** The adapters read POSIX paths on Linux, so the risk is
  low, but it is not covered.
- **Native resume is still `NOT_VERIFIED`** for every provider. Reading a
  session is not resuming one, and no release note here claims otherwise.
- **Provenance has no classifier for DSH/Grok**, so their events stay `unknown`.
  That is a coverage gap, not a regression.
- **VS Code extension is not distributed** (no VSIX). It is in the tree at 0.1.0
  and does not affect this release.
