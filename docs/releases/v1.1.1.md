# v1.1.1 — reliability and correctness patch

**Release candidate. Not tagged, not published.**

A patch release with no new features and no breaking change. It fixes five
confirmed defects, all found by reproducing them first, and it makes one
deliberate decision *not* to change the scan architecture.

## Fixes

**DSH native resume was advertised but could not run.** The adapter set
`can_resume = True` and stored `dsh --resume <id>`. `dsh` requires
`--profile <name>` before any application argument, and a session record carries
no profile, so the command could never be built. The user-visible result was two
surfaces contradicting each other: `verify --matrix` said `SUPPORTED` while
`voyager resume` refused the same session. The adapter, the matrix and the
READMEs now say what is true.

**`overview` read every candidate session's events and then kept twelve rows.**
1.724 s → 0.278 s, 10,016 statements → 28, identical output.

**`prune_missing_sessions` ran an unindexed lookup once per session, on every
scan.** The `sources` table's only key is `(provider, path, sid)`, so
`WHERE provider=? AND sid=?` used the `provider` prefix alone and scanned every
source row of that provider each time. Adding
`idx_sources_provider_sid(provider, sid, path)` takes prune from 13.17 s to
0.548 s on a 10,000-session index, and a whole no-op scan from **21.41 s to
1.61 s** — with an *identical* statement count, so the gain is the index and not
the machine. `scan_touch` 23.35 s → 3.41 s.

**A partially written multi-session artifact looked complete.** Cursor, ZCode
and Codex's app store yield many sessions from one path, and `source_changed()`
is satisfied by any single row for that path — so writing *k* of *n* sessions and
then being interrupted made the artifact look unchanged, and the remaining
sessions were never indexed again without `--force`. Reproduced on a two-session
ZCode database, with a per-file control that heals. Freshness is now recorded
only once the whole artifact has landed.

**The recorded fingerprint could describe content that was never read.** The
fingerprint was taken *after* the source was read (and, for a multi-session
artifact, after the whole artifact had been written), so anything a provider
wrote in between was recorded as though it had been indexed — and the next scan
saw "unchanged". The window for a large artifact is the whole read, which for
`voyager watch` means scanning in the background next to a running agent. The
fingerprint is now taken before the read.

**One failing write aborted the whole scan.** A single locked provider database
threw away the entire round — including every other provider, which was never
scanned at all. Writes are now isolated per session, an artifact is never
stamped fresh unless every session that claims it was written, and failures are
reported. A burst of failures that clears does not stop the scan; failures that
are both numerous *and* persistent still do, loudly.

**Opening the index required the write lock.** `Store.__init__` ran two
unconditional no-op writes, so with anything else writing to the index a
foreground `voyager scan` / `continue` / `status` could die at startup with an
unhandled `database is locked` after the 5 s timeout. Both writes are now
guarded by a read, so a current index opens without ever asking for the write
lock.

## Compatibility

**Patch-appropriate: no breaking change.** No public function or CLI signature
changed. `BRIDGE_SCHEMA_VERSION` is still `1` and the integration-info contract
is unchanged, so the DSH plugin needs no update. The only persistence change is
one additive index; no column, no data migration, and existing databases are
unchanged apart from gaining that index.

One upgrade note: the index is built the first time an existing index database is
opened after upgrading. It is a one-off cost proportional to the size of the
`sources` table and it happens on the first `voyager scan`, not at import.

## Deliberately not in this release

* **Batched scan transactions.** Measured ceiling: one commit costs 0.25 ms, so
  10,000 of them are 2.49 s of a 71.9 s write path — about **1%** of a full
  re-index — in exchange for making a batch the atomic unit. NO_CHANGE.
* **Streaming the materialised scan.** Peak RSS is ~4 KB per event (423 MB at
  100k events); the fix changes the adapter contract and moves parse errors into
  the write loop, which is the situation the partial-write defect is about.
  Deferred with a number and a design.
* **A scan lock, bounded retry, or provider/source-granular coordination.**
  Measured: two concurrent scans produce **zero** lock contention and every
  concurrency scenario converges. There is no defect to fix, and a second lock
  model would be a second thing to get wrong.
* **Merging the two capability models** (issue #16).

## Known limitations, stated rather than hidden

* A source changed by something that preserves **both** size and mtime (a backup
  restore, `rsync -t`, `cp -p`) is not detected until it changes again. Nothing
  short of reading every file can see it, and reading every file on every scan
  would defeat the fingerprint: measured at 122 s against 1.6 s for the no-op
  scan. `--force` re-reads.
* If a writer holds the index for the whole of a scan, the scan completes having
  written nothing and says so; a later scan indexes everything. The round is
  lost, the data is not.
* The extended release workflow has still **not** been exercised against a real
  tag. This release is its first real test.
