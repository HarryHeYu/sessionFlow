# sessionFlow Reliability Hardening Report

**Baseline** `f7967a0`. **Nothing was tagged, published, or pushed to PyPI/npm.**

Four confirmed defects, each reproduced before it was fixed. Two of them were
found by this round's own investigation rather than from the previous round's
notes. The scan architecture was **not** refactored, and two of the round's
proposed directions ended in an explicit decision *not* to change code.

Design contract and full measurements: [`docs/SCAN_CONSISTENCY.md`](../SCAN_CONSISTENCY.md).

## 2. D6 — one failing source took the whole scan with it

Measured before any change (`E:\sessionflow-scratch\p14\probe_d6.py`):

| scenario | result |
|---|---|
| per-file, write fails on source 2 of 3 | **scan aborts**; source 3 never processed |
| per-file, *parse* fails on source 2 of 3 | scan completes, 2 of 3 indexed |
| multi-session, write fails on session 2 of 3 | scan aborts; 0 source rows (artifact correctly unstamped) |
| two providers, the first one's write fails | **the second provider is never scanned at all** |
| plain re-scan after any of the above | converges |

The defect was not "errors are fatal" — parse errors were already isolated. It
was that the **write** path is unguarded and the adapter loop above it is
unguarded too.

**Decision: per-session isolation, with the source kept incomplete.** The write
is already one transaction per session, so that is the natural granularity and it
costs nothing semantically. The rule that makes it safe is the one the round
insisted on:

> an incompletely written multi-session source is **never** stamped complete.

A failed bundle's path is withheld from `stamp_sources()`, so for a shared-path
artifact (Cursor, ZCode, the Codex store) one failure withholds the stamp for the
whole artifact and the next scan re-reads it. Stamping the survivors — the
obvious implementation — would make the artifact look complete and strand the
failed session: D5 one layer up.

Effects, as required by the round:

* **fingerprint** — the failed write rolls back with its source row, so the file
  keeps its previous fingerprint and `source_changed()` stays true.
* **prune** — unaffected. `disk_paths` comes from `discover()`, so a source we
  failed to *write* is still a source we *saw*; it is never marked
  `SOURCE_MISSING`.
* **retry** — the next plain scan retries it. No `--force`.
* **consistency** — unchanged; every session is still one transaction.

A second unguarded writer turned up while testing this: `prune_missing_sessions`
writes on **every** scan, so a scan with nothing to do could still die — and it
did, with a traceback, while another process held the lock. prune and the
post-scan continuity pass are derived and idempotent, so they are now guarded
too: the index is written, and the next scan redoes the bookkeeping.

**Bounded, not unbounded.** `MAX_WRITE_FAILURES = 25` **and**
`WRITE_FAILURE_GRACE_SECONDS = 30`: failures must be both numerous *and*
persistent before the scan gives up. Measured why the grace is needed — a write
blocked by another process fails **immediately** (SQLite refuses to wait inside a
transaction that has already read), so 25 failures cost about a second, and a
bare count would abandon a lock that clears moments later. A blocked *prune*
does wait the full 5 s busy timeout.

## 3. D7 — the fingerprint described content that was never read

The real order was `stat → read → stat`, and the **second** stat was what got
recorded. Reproduced (`E:\sessionflow-scratch\p14\probe_d7.py`):

| scenario | before | after a plain re-scan |
|---|---|---|
| source appended after parse, before the write | recorded fingerprint == the file's actual fingerprint | **stuck** — the appended message is never indexed |
| multi-session artifact written by another process mid-read | recorded == actual | **stuck** — the late session is never indexed |
| same size **and** same mtime, different content | `new=0 unchanged=1` | stale content stays |

The second row is the serious one: the window is the whole `ad.scan()` call —
seconds to minutes for a large artifact — and `voyager watch` exists precisely to
scan in the background next to a running provider agent.

**Fix**: snapshot every discovered source *before* anything is read and record
that. A source that changed during the read then leaves current ≠ recorded, and
the next scan re-reads it. The snapshot is only taken on a round that is going to
read, so a no-op scan is unaffected — confirmed by `scan_inc` still measuring
**1.79 s** in §5. No transaction semantics moved.

**Not fixed, and why**: a change preserving both size and mtime. Nothing short of
reading the file can see it, and reading every file on every scan defeats the
fingerprint — measured at **122 s** for the 10,000-file corpus against **1.6 s**
for the no-op scan that reads nothing. `--force` remains the documented answer.
`ctime` would work on POSIX but is *creation* time on Windows, so it would make
the fingerprint mean different things per platform.

## 4. Concurrent scan — no defect found, no lock added

The round's premise was that the WorkThread lease is not a global scan lock. It
is not — it is WorkThread-scoped and `run_scan` takes no lease at all — and that
was already recorded in the contract (§4). Two real processes, one on-disk
index, 400 sessions in one ZCode artifact
(`E:\sessionflow-scratch\p14\concurrency_probe.py`). After every scenario:
sessions, `event_fts` vs `events`, `SOURCE_MISSING`, duplicate groups.

| scenario | result |
|---|---|
| two scans, same provider, same index | both rc=0, **0 lock messages**, all checks OK |
| two scans, different providers, same index | both rc=0, all checks OK |
| another process holds a write transaction for 8 s | rc=0 (was rc=1 with a traceback), all checks OK, converges |
| one scanner killed mid-scan while another scans | killer rc=137, survivor rc=0, all checks OK |

**No duplicated events, no lost sessions, no false `SOURCE_MISSING`, FTS
consistent, every scenario converges.** The failures that existed were ours, not
SQLite's: a contended write aborted the scan (§2), and opening the index needed
the write lock.

**That last one was a new finding.** `Store.__init__` ran two unconditional no-op
writes — the `meta` insert and the O2 backfill `UPDATE` — so *every* entry point
(`scan`, `continue`, `status`, the MCP tools, the DSH bridge) needed the write
lock just to open the index. Reproduced: a scan exited 1 with a traceback at
`store.py:391` while another process held the lock. Both writes are now guarded
by a read, so a current index opens without the write lock while a legacy
database still migrates.

**Decision: no scan lock, no bounded-retry layer, no provider/source-granular
coordination.** There is no measured defect for them to fix, and the D13 lease is
not reused as a scan lock — different scope, different lifetime, and a second
lock model is a second thing to get wrong. Known bounded limitation, recorded
rather than hidden: if a writer holds the index for the whole of a scan, the scan
completes having written nothing and says so; a later scan indexed all 400.

## 5. Large-scale benchmarks

`scripts/benchmark.py` (the existing harness, unchanged), Windows, Python 3.13.12.

**10,000 sessions / 100,000 events** (`codex_src10k`):

| task | wall | CPU | peak RSS | statements | transactions |
|---|---|---|---|---|---|
| `scan_initial` | 97.21 s | 75.20 s | 423.1 MB | 320,021 | 10,001 |
| **`scan_inc`** (nothing changed) | **1.79 s** | 1.61 s | 422.8 MB | 40,019 | 0 |
| `scan_touch` (20 files touched) | 3.96 s | 3.34 s | 423.4 MB | 50,581 | 21 |
| `scan_force` | 101.44 s | 74.58 s | 423.5 MB | 320,021 | 10,001 |

Index size 180.9 MB. `scan_inc` repeats at 1.765 / 1.937 / 1.823 s (spread
0.17 s), so these are reproducible rather than single samples.

| scenario | result |
|---|---|
| 20 sessions **added** to the tree | 1.82 s, statements +80 — only the 20 new sources were touched |
| 20 sessions **appended** | 1.69 s, statements +80 |
| killed mid-scan (500 of 10,020 written), then a plain re-scan | **10,020 sessions, 0 duplicate groups, `fts` 100,180 == `events` 100,180** |

**The ~3 GB memory question.** Peak RSS is ~4 KB per event on this dataset
(423 MB at 100,000 events), and `docs/PERF_O1.md` recorded 2,971.7 MB at
1,000,000 events. Nothing in this round touched materialisation, so that risk is
**unchanged and still open** — it is the `SCAN_MATERIALISE_ALL_BEFORE_WRITE`
debt, deferred in §7 with a design and a number rather than quietly dropped.
The 100,000-session / 1,000,000-event run was started and had not completed when
this report was written; it is not reported as a result.

## 6. Crash consistency — the five invariants still hold

Re-verified on a real disk database, with a real child process terminated by
`os._exit` so nothing unwinds:

| invariant | evidence |
|---|---|
| **I1** atomic session ingest | a kill inside a session transaction leaves `(sessions, events, sources) == (0, 0, 0)` |
| **I2** no duplicate events | `dup_groups=0` after a killed 10,020-session scan, after two concurrent scans, and after a transient lock |
| **I3** marking non-destructive and reversible | prune is still mark-only; a failed prune leaves the index intact |
| **I4** re-scan converges | killed scan: 500 written → 10,020 indexed; every concurrency scenario converges; D5/D6/D7 tests all assert convergence without `--force` |
| **I5** `--force` is an accelerator | the D5, D6 and D7 fixes removed the three cases where `--force` was the only way back |

No provider session file is ever modified: provider databases are opened
`mode=ro`, and the only writes are to the index.

## 7. v1.1.1 release candidate

**Patch-appropriate. No breaking change.** Candidate contents (commits since
`v1.1.0`): `5c68d73`, `d60eb3e`, `7541a93`, `c5bfeda` and this round's changes.

* No public function or CLI signature changed.
* `BRIDGE_SCHEMA_VERSION` is still `1`; the integration-info contract gained no
  keys, so the **DSH plugin needs no update**.
* The only persistence change is one additive index. No column change, no data
  migration.
* Upgrade note: the index is built the first time an existing index database is
  opened. One-off, proportional to the `sources` table, on the first `voyager
  scan` — not at import.

**Excluded on purpose**: batched transactions (measured ceiling ~1% of a full
re-index, against making a batch the atomic unit), streaming materialisation
(changes the adapter contract; deferred with a design), any new lock model (no
defect to fix), and merging the two capability models (#16).

### Release workflow audit

| property | verdict |
|---|---|
| builds from the tag tree | ✓ `checkout@v4` on a tag push; `python -m build` |
| tests pass before the build | ✓ separate step before it; any failure stops the job |
| artifact version == tag | ✓ explicit assertion, plus a leak check for `tests/`/scratch |
| draft Release lifecycle | ✓ created `--draft`, published only at the end |
| safe retry after failure | ✓ existing Release untouched, assets skipped, `cancel-in-progress: false` |
| never overwrites an asset | ✓ checked by name before upload; no `--clobber` |
| no PyPI / npm | ✓ |

**One gap found and fixed**: publishing was gated on "did *this run* create the
Release", so a retry after a failed upload attached the missing asset and then
stopped, leaving a draft nobody would publish. Publishing is now keyed on the
Release actually being a draft, with an explicit refusal if any asset is
missing; an already-published Release is still never touched. Static validation
(YAML shape, `bash -n` on every block, the embedded Python compiles, the safety
properties, and the GitHub-context check that rejected an earlier revision) all
pass.

**It has still never run against a real tag.** This release would be its first
real test. If it fails, the tag must not be moved; fix the workflow and re-run
against the same tag — the workflow never overwrites an existing asset, so a
re-run is safe.

## Final status

**COMPLETE.**

Four defects reproduced and fixed, each with a test that failed first; one of
them (D8) was not on the round's list at all and was found by testing the
concurrency claim rather than assuming it. Two of the round's proposed directions
— a scan lock and a retry layer — ended in an explicit decision *not* to add
code, on measurement. The scan architecture was not refactored, no tag moved, and
nothing was published.

The goal was to make sessionFlow recoverable under concurrency, source change,
abrupt termination and long-running large-scale use. On the evidence: it already
was, in the SQLite layer — what it could not survive was *our* reaction to a
contended write, and that is now bounded, reported and self-healing.
