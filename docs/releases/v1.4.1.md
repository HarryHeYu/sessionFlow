# Voyager v1.4.1

Patch release, **2026-11-14**. Five cold-start reliability fixes found by the
v1.4.0 first-install acceptance (#29, #34–#37, #42). No schema change — the
core bridge schema stays `1`, so this is fully compatible with the DSH plugin
**v1.2.0** (which requires schema `1`); no plugin change is needed.

## What's fixed

**A corrupt or unusable index is reported, not thrown at the user.** A file
that exists but is not a usable SQLite database made every command that merely
opens the store — `list`, `status`, `search`, `scan`, `continue`,
`thread list` — die with a raw `sqlite3.DatabaseError` traceback, while
`doctor` and `db check` rendered the same situation cleanly. The store now
converts exactly the unusable-file signatures into a typed error the CLI
renders as one line:

```text
error: index database at …\index.db is unreadable: file is not a database
  run `voyager db check` for details and restore from a backup (`voyager db backup`).
```

The conversion is scoped to those signatures (a `ProgrammingError` from our
own SQL still surfaces as itself), the `OperationalError` retry arm is
untouched, and the corrupt file is never rewritten or removed — it is the
evidence for `db check` and a backup restore. [#34](https://github.com/HarryHeYu/sessionFlow/issues/34) · [#38](https://github.com/HarryHeYu/sessionFlow/pull/38)

**Read-only `thread` and `checkpoint` subcommands no longer create an index.**
`voyager thread list` used to create an empty `index.db` in a home without
one — the one surface that broke `open_read`'s documented "a read does not
create a database" guarantee; `voyager thread checkpoint list/show/export`
did the same and additionally ran schema DDL behind a read. Both now use the
read path: no index → an in-memory store whose checkpoint schema is created
in memory only; a database predating checkpoints degrades to the empty
answer instead of being migrated by a read; a corrupt index fails cleanly
instead of looking like "no checkpoints". Mutating subcommands
(`create` / `attach` / `close` / `reopen` / `archive` / `unlock`,
`checkpoint create/update/import`) keep writing exactly as before.
[#35](https://github.com/HarryHeYu/sessionFlow/issues/35) · [#39](https://github.com/HarryHeYu/sessionFlow/pull/39) · [#42](https://github.com/HarryHeYu/sessionFlow/issues/42) · [#43](https://github.com/HarryHeYu/sessionFlow/pull/43)

**A scan that cannot write names the file it cannot write to.** SQLite
reports only "attempt to write a readonly database". With the db writable and
a stale read-only `-shm` — which SQLite creates with the db's mode while the
db was read-only, on Linux — every scan kept promising a retry that could
never succeed, and nothing said why. The summary now carries the diagnosis
(read-only mode-bit probes; nothing is chmodded or removed):

```text
1 session(s) could not be written; the index is consistent and nothing was
half-written. The next scan retries them once the cause above is resolved.
  first write failure: OperationalError: attempt to write a readonly database; unwritable: index.db-shm
```

When the probe finds every file writable (root bypasses mode bits; ACLs,
immutable flags and mount options live below them), it says so instead of
staying silent. Restoring access and re-scanning verifiably lands the pending
session. [#36](https://github.com/HarryHeYu/sessionFlow/issues/36) · [#40](https://github.com/HarryHeYu/sessionFlow/pull/40)

**QUICKSTART no longer promises a file the D7 shortcut does not write.** The
§6 example `continue --thread <thread> --no-launch -o …` reads as if a package
always appears; on a thread whose newest live session is natively resumable,
decision D7 prints the resume command and compiles nothing. The example now
carries the expectation and the `--bundle` form that forces the package.
[#37](https://github.com/HarryHeYu/sessionFlow/issues/37) · [#41](https://github.com/HarryHeYu/sessionFlow/pull/41)

## Compatibility

- Bridge schema stays `1`; the DSH plugin **v1.2.0** (six tools) needs no
  change. The Evidence `verify` API op is **not** in this release — it is
  still an open Draft ([#24](https://github.com/HarryHeYu/sessionFlow/pull/24)).
- Index compatible in both directions with v1.4.0 / v1.3.1 / v1.3.0: no schema
  change, no migration. Rolling back is safe.
- Known limits, unchanged and stated: a read-only-period scan can still leave
  a stale read-only `-shm` behind (the fix is the diagnosis, not auto-repair);
  native resume remains `NOT_VERIFIED` on every provider; OpenCode evidence
  beyond v2.0.29/Windows is still pending (#30).
