# Post-v1.1.0 Engineering Hardening — Audit and Delivery

**Date:** 2026-10-13 · **Base:** v1.1.0 (`b0d8fc8` core / `4e867bf` plugin) ·
**Scope:** audit first; code changed only where a defect was proven.

No tag was moved and no release was published. Four defects were confirmed and
fixed; everything else is reported rather than patched.

The instruction was to separate four things and not to treat "unverified" as
"broken". Here is the split for the two repositories at `main` today.

### Implemented and verified

| Area | Evidence |
|---|---|

### Implemented but **not** truly verified

| Area | What is missing |
|---|---|
| **Native resume, all providers** | The command is built and its argument surface is verified (§2); no resume has been observed resuming the intended session, because doing so needs credentials and would create sessions in a real environment. |
| Extended release workflow | Never run against a real tag — that would mean cutting one. |
| `sessionflow_merge` auto-selection | A live turn answered correctly without calling it. |

### Confirmed defects — all four fixed in this round

| # | Defect | Class |
|---|---|---|
| D1 | DSH adapter declared `can_resume = True` and stored `dsh --resume <id>`, a command that cannot run | user-visible correctness |
| D2 | Benchmark harness ran `scan_inc`/`scan_touch` against `:memory:`, so they measured **cold** scans | measurement correctness |
| D3 | Benchmark harness `overview` task was time-dependent (48 h default window vs an ageing dataset) | measurement reproducibility |
| D4 | `api.overview` was an N+1 — 10,016 statements to return 12 rows | product performance |

### Design debt only — reported, not touched

- **#16** two capability models (see §5).
- `SCAN_MATERIALISE_ALL_BEFORE_WRITE` — bounds the scan by RAM; needs a streaming design.
- `SCAN_BATCH_TRANSACTION_OPTIMIZATION` — needs a crash-consistency design before any code; today a killed scan loses at most one session.
- `STARTUP_GIT_SUBPROCESS_AMPLIFICATION` — scales with distinct workspaces, not sessions.
- Plugin peer-range prerelease trap (see §5).

## 2. Native Resume verification matrix

Verified **without credentials**, by checking each constructed command against the
provider CLI's own argument surface on this machine. Nothing was launched into a
real session.

| provider | adapter declares | constructed command | native id source | CLI surface | result |
|---|---|---|---|---|---|
| **codex** | `can_resume = True` | `codex resume <uuid>` | rollout `session_meta.session_id` (UUID) | `codex resume [SESSION_ID] [PROMPT]` — accepted, reached the TUI | **command valid**, resume not observed |
| **claude** | `can_resume = True` | `claude --resume <uuid>` | JSONL filename stem (UUID) | `-r, --resume [value]` documented | **command valid**, resume not observed |
| **grok** | `can_resume = True` | `grok -r <uuid>` | `summary.json` → `info.id` (UUID) | `-r, --resume [<SESSION_ID_OR_TITLE>]` — accepted, started | **command valid**, resume not observed |
| **dsh** | ~~`True`~~ → **`False`** | ~~`dsh --resume <session-uuid>`~~ → none | `session-<uuid>` | **`dsh --resume <id>` exits 1: `error: --profile <name> is required`** | **was broken — fixed** |

### D1, in full

`dsh --help` lists no `--resume` option at all; the flag is an *app* argument that
follows the launcher flags, and the documented form is
`dsh --profile tui --resume <session>`. The session path is
`~/.dsh/sessions/<munged-cwd>/session-<uuid>/` and the record carries `cwd` and
`agentPreset` — **never a profile**, so Voyager cannot build a command that runs.

The user-visible consequence was an inconsistency between two surfaces:

```
$ voyager verify --matrix
dsh  …  SUPPORTED          <- native_resume
$ voyager resume session-8f08216f
Resume unsupported for provider 'dsh'.          <- the CLI refused the same session
```

Fixed by making the adapter's declaration match what it can actually do, and by
dropping the dead `resume_cmd` (which `voyager show` used to print).

## 3. Issue #12 — performance baseline and results

### Method

`scripts/benchmark.py`, cached datasets on the repo's own drive. The sandbox
charges ≈1.3 s per process start, so **counters** (`execute`, `txn`,
`subprocess`, `git_calls`) are the portable evidence; wall clock is reported
beside them, never instead of them.

### Scan path — 10,000 sessions / 100,000 events, file-backed

| task | wall s | cpu s | peak RSS MB | subprocess | git_calls | execute | txn |
|---|---|---|---|---|---|---|---|
| `scan_initial` | 104.32 | 84.17 | 542 | 3 | 10,000 | 320,018 | 10,000 |
| **`scan_inc`** | **21.41** | 20.16 | 408 | 0 | 0 | 40,019 | **0** |
| **`scan_touch`** | **23.35** | 22.19 | 414 | 0 | 20 | 50,579 | 20 |
| **`scan_force`** | **130.58** | 99.17 | 414 | 3 | 10,000 | 320,018 | 10,000 |

**Incremental is 6.1× faster than forced** (21.41 s vs 130.58 s) and writes
**zero** transactions — which reproduces the O1 report's 5.2× claim on a fresh
machine state, and does so from the standard `run` command for the first time.

### D2 — the harness was measuring a cold scan

`run_suite` passed `":memory:"` for the scan jobs. `_scan_setup` seeds
fingerprints and then **closes** its `Store`; with an in-memory database the
fingerprints go with it, so the measured pass saw every source as new.

| `scan_inc` | wall | cpu | git_calls | execute | txn |
|---|---|---|---|---|---|
| before (as `run` measured it) | 78.57 | 67.50 | 10,000 | 330,018 | **10,000** |
| after (file-backed, fixed) | **21.41** | 20.16 | **0** | **40,019** | **0** |

A 3.7× error, attributed to the incremental path, on the same dataset and machine.

### D3 — the `overview` task changed with the calendar

`api.overview` defaults to a 48-hour window and the synthetic datasets are
generated once and then age. On 2026-10-02 the 10k dataset was fresh and the task
issued `q=2806` (the documented N+1); on 2026-10-13 the same dataset was 258 h
old, every session fell outside the window, and the same task issued `q=4`.
Pinning the window makes the number mean one thing. This is how a live N+1 gets
mistaken for a fixed one — which is nearly what happened here.

### D4 — `OVERVIEW_RECENT_SESSIONS_N1`, fixed

`api.overview` read every candidate session's events and then kept 12 rows. Its
recorded reason for being left alone — *"the wall-clock cost is dominated by
sandbox spawn overhead, not the query"* — was read off a run whose `subprocess`
count was **zero**.

| `overview` on syn10k | wall s | cpu s | subprocess | `q` | execute |
|---|---|---|---|---|---|
| before | 1.724 | 1.125 | 0 | 10,016 | 10,016 |
| after | **0.278** | **0.203** | 0 | **16** | **28** |

6.2× faster wall, 5.5× less CPU, 626× fewer queries — with byte-identical output
(the same 12 rows, same order, same fields). The debt entry is removed from
`voyager doctor`, and the O4 test now asserts it does **not** come back.

### What was deliberately not optimised

`SCAN_MATERIALISE_ALL_BEFORE_WRITE` and `SCAN_BATCH_TRANSACTION_OPTIMIZATION`
stay as they are. Both change crash-recovery semantics, and the current
per-session transaction boundary is what makes an interrupted scan safe. The
1M-event run remains `ENVIRONMENT_LIMITED`; it has still not been re-run.

## 5. Provider and capability compatibility

### Issue #16 — two capability models

**No new user-visible inconsistency.** `tests/test_capability_consistency.py`
passes: no user-facing module reads `voyager.integrations.capabilities`, and
doctor resolves every explanation from the canonical matrix. The two models still
answer different questions with similar words (`startup_hook` vs
`has_session_start_hook`), which is the hazard the issue describes — so #16
remains **design debt**, exactly as it was framed, not a defect.

### Plugin `peerDependencies`

| declared | actually installed | verdict |
|---|---|---|
| `@deepseek-ai/cordis: 4.0.2` | `dsh 0.1.5-rc.3` depends on `@deepseek-ai/cordis: 4.0.2` | **exact match** |
| `@deepseek-ai/dsh-tools: ^0.1.5-rc.3` | the `@deepseek-ai/dsh-*` packages ship as `^0.1.5-rc.3` | **match** |

`dsh --version` → `0.1.5-rc.3`, the version the README and release notes name.

**The prerelease trap is real, and was left alone.** Verified with node-semver:

```
^0.1.5-rc.3      matches 0.1.5-rc.3 ✅, 0.1.5-rc.4 ✅, 0.1.9 ✅
                 excludes 0.1.6-rc.1 ❌, 0.2.0-rc.1 ❌
>=0.1.5-rc.3 <0.2.0-0   also excludes 0.1.6-rc.1 ❌
```

So a future `0.1.6-rc.*` would fail to resolve. Widening the range is exactly
what the brief forbids doing on the strength of a semver edit alone, and there is
no `0.1.6-rc.*` to install and test against, so **nothing was changed**. It is
recorded here and in `docs/community/submission-targets.md` for the next DSH bump.

## 8. Is v1.1.1 warranted?

**Yes — but it is your call, and nothing was published.**

The case for a patch release:

1. **A user-visible capability correction.** `verify --matrix` told users DSH
   native resume was SUPPORTED while `voyager resume` refused the same session.
   Anyone reading the matrix was misinformed.
2. **A measured read-path improvement.** `overview` is 6.2× faster with 626×
   fewer queries, with identical output.
3. **Corrected measurement tooling.** The benchmark now measures what its task
   names say, which is what #12 said a future attempt needs first.

The case against releasing *right now*: the extended release workflow has still
never run against a real tag. A v1.1.1 tag would be its first live exercise — if
that is not wanted yet, the fixes can sit on `main` and ship with the next
release.

Nothing was tagged, moved or published in this round.
