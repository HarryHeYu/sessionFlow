(`USERPROFILE` / `HOME` / `APPDATA` / `LOCALAPPDATA` all redirected), its own
index, its own git repository, and two controlled synthetic sessions. The
operator's real `~/.voyager/index.db` was measured before and after and did
**not** change (`1869410304` bytes, mtime `21:33:32` throughout).

| F | Full continuation context | **PASS** — `voyager continue` resolves the newest session; `voyager handoff --to codex` writes a Context Package carrying the goal, the **stop point with the TODO**, files touched, commands run and the timeline |

### Install-documentation claims, each verified

Python ≥ 3.10 ✅ · Node ≥ 22.19 ✅ · `allowBuilds` must use the **exact key pnpm
prints** (including the resolved commit) ✅ · profile creation then `add` then
`--dump-config` ✅ · core executable selection — a **configured** `voyagerBin` is
authoritative and failure is reported rather than silently falling back ✅ ·
explicit `--db` path ✅ · no-credential behaviour — DSH stops with
`MISSING_CREDENTIAL`, which is the host's configuration ✅ · Windows vs Linux —
`USERPROFILE` drives `Path.home()`, `APPDATA` is needed by some adapters ✅ ·
core/plugin version relation — released together at v1.1.0 over bridge schema 1 ✅

**One correction found and documented:** `VOYAGER_DB` is **not** a global CLI
override (only the verification harness reads it). Isolation requires the `--db`
flag. This is recorded in the demo README so the next person does not repeat it.

## 5. Release automation

`.github/workflows/release.yml` (core) now does:

```
tag → checkout exact tag → full suite → build wheel + sdist from the tag tree
    → twine check → assert version == tag and no tests/scratch in the wheel
    → create the Release as a DRAFT → attach assets → publish
```

| Requirement | How it is met |
|---|---|
| Built from the tag tree | `actions/checkout` of the tag, then `python -m build` |
| Version matches the tag | asserted from the wheel's `METADATA` against `GITHUB_REF_NAME` |
| No tests/scratch/private content | the wheel is asserted clean; the sdist is asserted free of scratch/`.git` (it ships `tests/` **on purpose** — that is how a consumer runs them) |
| Verifiable artifacts | `twine check` + the version assertion + sizes/`sha256` visible on the Release |
| No PyPI / no npm | no publish step of any kind |
| No long-lived token | `GITHUB_TOKEN` only, `permissions: contents: write` |
| Never overwrites an asset | an asset that already exists is skipped, and `--clobber` is absent |
| Reruns / partial uploads | an existing Release is left untouched; a rerun attaches only what is missing |
| Concurrency | `cancel-in-progress: false` |
| Failure announces nothing | the Release stays a **draft** until every asset is attached |

**Verification done:** static validation (YAML shape, `bash -n` on every shell
block, the embedded Python compiles, no PyPI/npm/`--clobber`/tag-moving text) and
a behavioural simulation against a stub `gh` covering three scenarios — fresh
(create → attach both → publish), rerun (nothing created, nothing replaced, not
re-published) and partial (only the missing asset attached). All passed.

**Verification NOT done:** it has **not** run against a real tag. Doing so means
cutting a tag, which is out of scope here. The first tag after v1.1.0 is the true
test; this is stated at the top of the workflow file itself.

**A real defect was found and fixed on the way.** The first revision was rejected
by GitHub:

```
Invalid workflow file: .github/workflows/release.yml#L1
(Line: 55, Col: 13): Unrecognized named-value: 'runner'
```

A job-level `env` cannot read the `runner` context. The artifact directory now
comes from `RUNNER_TEMP`, a default variable available to every step. The local
validator gained a check for this class of error, so it fails locally instead of
on push.
